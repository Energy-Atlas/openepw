# OpenEPW v0.1 Stage 2 Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` for native execution
> task by task after owner approval. Tasks below are working/testable increments,
> not additional human approval gates. Follow the handoff's intervention rules.

**Goal:** Deliver the agreed Python-first v0.1 with transparent retrieval, EPW/QC,
two distinct future-weather methods, REST, durable local jobs, MCP and a small CLI.

**Architecture:** One domain/service layer, provider/generator protocols, pandas
weather tables and typed JSON schemas. SQLite/filesystem jobs and thin adapters.
Optional climate/server dependencies keep EPW-only use light.

**Tech stack:** Python 3.11+, Hatchling, Pydantic v2, pandas/numpy, httpx, pytest,
Ruff, mypy; optional FastAPI/uvicorn, official MCP SDK, xarray/zarr/fsspec/gcsfs,
cftime, PsychroLib/pvlib and cdsapi/NetCDF.

**Spec:** [human brief](../20260920-openepw-brief.md),
[architecture and schemas](../../ARCHITECTURE.md),
[scientific methods](../methods/future-weather.md), [EPW contract](../methods/epw-conventions.md).

**Approval status:** Approved by the owner on 2026-09-20. Implement autonomously
until v0.1 is substantially complete. The owner will be unavailable: investigate,
flag and skip unresolved datasets; collect minor issues and reminders in the
execution record. Stop only for a major unresolved blocker after reasonable
attempts, or an applicable irreversible/security boundary. No routine checkpoints
require a response. Preserve the current `feature/stage-1-validation` branch.

## Stage 1 findings and proposed scope

All six targets were contacted; see the [feasibility matrix](../providers/README.md)
for auth, years, resolution, variables and [dated evidence](../validation/README.md).

| Validation result | Implementation implication |
| --- | --- |
| Open-Meteo ERA5: 48 hours, nine variables without nulls | First normalized historical EPW provider; no unannounced best-match blend |
| PVGIS: full native TMY JSON + EPW | First native-product provider; retain mixed source/year metadata |
| OneBuilding: catalog + full Ithaca TMYx ZIP | Add discovery/retrieval; keep redistribution unverified, no repository fixtures/mirror |
| NOAA: 64 daily station reports | Add historical station retrieval with flags, hourly selection and explicit solar gaps; examine GHCNh successor |
| NSRDB: current NLR discovery works; CSV demands valid email | Production key/email needed for live fetch acceptance; legacy hostname failed DNS |
| CDS: public schemas work; tiny retrieval returns 401 | Optional direct access requires owner token and manually accepted terms |
| Pangeo CMIP6: matched historical/SSP245 metadata works | Validate multivariable numeric access early; large chunks need cost estimates |
| OEDI WRF: one 8,760-row/35-column future EPW read with ~7 MB transfers | Distinct hourly profile method feasible without full 9.1 GB archive download |

**Method A:** independent CMIP6 monthly shift/stretch implementation from published
equations. Exclude pyepwmorph direct reuse because of its MIT/AGPL module conflict;
FWG's NC-SA license also excludes code reuse. epwshiftr is an MIT reference, not a
mandatory R runtime. Full [reuse review](../methods/reuse-review.md).

**Method B:** coherent whole-year profile selection from Argonne's WRF/CCSM4
hourly trajectories. Initially published U.S. PUMA sites, RCP4.5/RCP8.5, and
2045–2054 or 2085–2094 only. Typical = multivariable year medoid; extreme =
documented heat/cold shock or persistence criterion; ensemble = temporal-year
trajectories, explicitly not multiple climate models. The user EPW provides site
and comparison identity; the source's paired baseline supplies calibration.
These capabilities must not be labeled global, SSP-based, unbiased or forecasts.

Four working provider integrations remain the target, with NOAA's missing-solar
limitations explicit; credentialed NSRDB is the preferred stronger U.S. actual-year
source. Direct CDS remains distinct from ERA5 through Open-Meteo. Blocked optional
access paths do not prevent the rest of v0.1. No provider is dropped silently.

## Global constraints

- Canonical package/import/CLI: `openepw`; software license MIT; Python 3.11+.
- No historical TMY/XMY synthesis; published products only on the retrieval side.
- No independent REST/MCP science, frontend, forced xarray/dask or distributed stack.
- Preserve actual source cells, periods, units, calendars, variable provenance,
  licenses, source checksums and requested-versus-resolved locations.
- No hidden data blending, timestamp repair, daily-to-hourly invention or SSP/RCP mapping.
- Config precedence: programmatic → environment → ignored local TOML; never persist secrets.
- Deterministic tests offline, live tests opt-in/provider-tagged; Windows/Linux/macOS.
- Commit at each meaningful deliverable with `fix(topic): description`, normal
  repository authorship, no history rewriting/destructive git.
- Use purpose-based branch prefixes (`feature/`, `fix/`, `refactor/`, `docs/`),
  never an agent/model/name or `codex/` prefix. Preserve the owner's current branch.
- Update FEATURES, ROADMAP, architecture/ADRs and provider/method docs as behavior lands.
- After approval continue through the plan; escalate only the eight handoff cases.

## Review focus

| Likely failure | Owning acceptance tests |
| --- | --- |
| UTC/local year edges, DST and Feb 29 corrupt 8,760/8,784 intervals | Tasks 2–3: energy/timestamp boundaries, partial vs annual validation |
| HTTP 200 contains empty/null or malformed provider data | Tasks 3–5: explicit unavailable/gap results, no false success |
| Dense points share a nominal cell but differ in elevation/options | Task 6: only scientifically identical requests deduplicate |
| Interrupted/partial jobs leak secrets or report success | Tasks 1, 7: redaction, durable per-item state and atomic writes |
| Climate scenarios, windows/calendars and ensembles are overstated | Tasks 8–9: capability errors, member coherence and provenance assertions |

## Execution conventions

Use the file layout and exact public signatures in ARCHITECTURE.md. Each task
starts with its named failing tests, implements the smallest working behavior,
runs the focused checks, updates docs and commits. Use `python -m pytest` in the
project environment. Test fixtures are explicitly synthetic unless their source
license/attribution is committed. Do not vendor Stage 1 scratch scripts into the
production package. Full offline suite/lint/type checks run before release readiness.

## Genuine external blockers and requested input

**No credentials are needed to begin Stage 2.** NSRDB live data acceptance needs
`OPENEPW_NLR_API_KEY` and `OPENEPW_NLR_EMAIL`. Direct CDS needs `OPENEPW_CDS_KEY`
and manual dataset-term acceptance. Configure these locally when available;
never paste secrets into the plan or chat. Work on other providers first.
See [credential setup](../providers/credentials.md) for account links, dataset
terms and the ignored local configuration handoff.

OneBuilding redistribution permission is unresolved. Default to local retrieval,
source notices and synthetic tests; public mirroring/bundling waits for evidence
of permission. pyepwmorph/FWG reuse issues are avoided by the chosen implementation,
so they do not block Stage 2. No account creation, purchase or publication is needed.

The main scope decision for approval is the bounded second future method described
above. If both methods must be global and SSP-based, that is a different requirement
and would require another data-source investigation. The present proposal follows
the brief's allowance for source-dependent feasibility and explicit limitations.
